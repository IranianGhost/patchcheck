# یادداشت ادامهٔ کار برای هم‌تیمی‌ها

> سند تاریخی تحویل مرحلهٔ اول (۲۰۲۶-۱۱-۱۰). مسیرهای `project/...` اکنون در ریشهٔ مخزن هستند.

دامنهٔ آماده
CLI و schemaها، snapshot دقیق و diff، چهار build، اجرای محدود و حفظ بایت‌ها،
oracle مستقل، replay، ddmin، corpus خودکار، دادهٔ خام ELF، گزارش و CI موجودند.
جزئیات فنی و امضای رابط‌ها در docs/architecture.md مرجع اصلی هستند.

کارهای مرحلهٔ دوم
۱. تحلیل قطعی diagnostics/ASan/UBSan، symbolization، نوع خطا و امضای پایدار:
   project/src/patchcheck/analysis.py، رابط analyze و match_failure.
۲. ارتباط مستند یافته با وصله، نگاشت خطوط و caller/callee:
   رابط correlate، دادهٔ diff و RunRecordها. نزدیکی به hunk به‌تنهایی علیت نیست.
۳. تفسیر و مقایسهٔ سخت‌سازی:
   project/src/patchcheck/elf.py و داده‌های خام NX/PIE/RELRO/Canary.
۴. اهداف و ارزیابی واقعی:
   دو برنامه، هشت نسخهٔ سناریویی، وصلهٔ ناقص و ندیده، oracleهای مستقل و
   ورودی‌های valid/boundary/invalid/new/minimized با منشأ و تأیید مدرس.
۵. اتصال نتایج تخصصی به pipeline و حذف قید stage-one فقط پس از کامل‌شدن
   همهٔ بررسی‌های الزامی؛ از فقدان شواهد PASS نسازید.

هماهنگی گروه
- همه از snapshot/history همین بسته شروع کنند و schema نسخه۱.۰ را هماهنگ تغییر دهند.
- برای کار جدید، branch شخصی بسازید و کد و آزمون مرتبط را با هم تحویل دهید.
- تقسیم نقش و نام اعضا را خود گروه بر اساس کار واقعی مشخص کند؛
  project/docs/contributions.md هنوز هیچ سهم انسانی انجام‌نشده‌ای را ادعا نمی‌کند.
- پیشنهاد مدرس و راهنمای دفاع در docs/teacher-proposal.md و docs/defense.md هستند.
- فایل GitHub Actions آماده است؛ اجرای واقعی GitHub به علت نبود remote انجام نشده.
- تأیید مدرس، امتیاز نهایی پروژه و کامل‌بودن تحلیل امنیتی ادعا نشده‌اند.

نکتهٔ ثبت شواهد
دادهٔ fixture برای آزمون چارچوب است. آن را به‌عنوان آسیب‌پذیری واقعی یا نتیجهٔ
نهایی امنیتی ارائه نکنید. اصل stdout/stderr، ورودی‌ها، hashها و شکست‌ها را حفظ کنید.
